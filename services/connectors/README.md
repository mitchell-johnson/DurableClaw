# Private connector service

The application binds to `durable-claw-connectors` using the named `ConnectorEntrypoint` entrypoint. This service has no public route, workers.dev address, or preview URL; its default HTTP entrypoint returns 404. Its credential vault binding is not available to the main application. The trusted app signs short-lived owner assertions with `CONNECTOR_AUTH_SECRET`, a dedicated secret shared only by these two deployments. Every vault independently validates and pins the organization, workspace, and owner tuple.

`ConnectorVault` stores encrypted OAuth credentials and PKCE verifiers in SQLite. AES-GCM authenticates the owner tuple, connection ID, provider and format version; HKDF derives keys from a separate `CONNECTOR_CREDENTIALS_SECRET`. Keep the encryption secret stable and backed up in your secret manager. Replacing it without a migration makes existing credentials unreadable. Both connector secrets require at least 32 characters of cryptographic randomness. OAuth client credentials and refresh tokens stay in this private service. The native TypeScript gogcli port executes inside the credential DO. Its per-invocation runtime attaches short-lived access tokens only to approved Google API destinations.

The owner chooses Google services. The Sheets bundle includes `bigquery.readonly` for Connected Sheets create/update/refresh operations, as required by the [Google guide](https://developers.google.com/workspace/sheets/api/guides/connected-sheets); the user also needs the relevant billing project and BigQuery IAM permissions. `google-services.json` is an unmodified export of the pinned fork's `gog auth services --json`; `google-metadata.ts` adds the explicitly requested write scopes and is shared with the application UI. Authorization uses an exact configured HTTPS redirect, 256-bit state, S256 PKCE, a ten-minute expiry, single-use consumption, and verified Google identity. Credentials retain the exact granted services and scopes. Reconnecting an account matches Google's immutable subject, not its email address. Refresh and disconnect operations serialize with execution. Disconnect deletes credentials before attempting provider revocation and leaves previous command receipts available.

General `gog_execute` requests require an exact approved invocation from the application. The vault reserves a durable receipt before executing and never automatically retries an uncertain action. A repeated invocation with different arguments fails; a matching completed invocation returns its saved result. The ledger retains at most 512 KiB per result and 32 MiB of results per owner. Larger responses are returned once and leave a completion tombstone. Tombstones do not expire; reaching 10,000 invocations fails closed and requires an operator retention/migration decision. Interrupted requests become `unknown` after a vault restart. Query `GET /v1/invocations/:id` to inspect an outcome without repeating an action. The three fixed Gmail read tools remain available without write approval.

Failed temporary-image cleanup retains at most eight validated Drive file IDs and public-permission indicators in the durable receipt. These diagnostics survive service reconstruction and ordinary result eviction; ordinary completed results are displaced within the same storage budget when necessary. The invocation remains `unknown` and cannot dispatch again. Owners can inspect the receipt through `get_service_invocation` and use a separately approved Drive command to recover. Raw provider errors and credentials are never retained as cleanup diagnostics.

The native command parser accepts only catalogued commands and typed arguments, including bounded input/output file references. Requests and complete responses are limited to 8 MiB, with up to eight input files totaling 4 MiB. The application persists returned artifacts in the owner's workspace. Catalog requests never contain credentials. Provider HTTP requests reject redirects, bound both headers and response bodies, and have hard deadlines. The vault returns generic errors and does not log upstream errors or secret-bearing bodies.

Google still enforces account roles, enabled APIs, organization policies, app verification, quotas and service restrictions. Google Photos only exposes supported app-created/selected media. CLI runtime administration, login and local configuration are not exposed as cloud agent commands.

Keep uses optional Workspace domain-wide delegation. Set the service-only `GOOGLE_WORKSPACE_SERVICE_ACCOUNT_JSON` secret and the exact `GOOGLE_WORKSPACE_DOMAIN` variable; a Workspace administrator must separately grant that service account the exact `https://www.googleapis.com/auth/keep` scope. The owner still signs in through Google OAuth and must have a verified email in that domain. The vault mints a short-lived Keep token from an RS256 service-account assertion using only the stored verified owner email as subject. The assertion audience and token endpoint are fixed Google URLs, the scope is Keep-only, and the service-account key never leaves the credential DO. Before every delegated mint, the vault rechecks the current OAuth token against Google userinfo and requires the verified email and immutable subject to match their encrypted stored values. A renamed or reassigned account requires reauthorization. Neither command arguments nor the agent may select another delegated subject. Keep connection attempts fail when this optional deployment configuration is absent. `GET /v1/capabilities` exposes only whether delegation is configured.

Some Gmail settings methods also require Workspace delegation: delegates, auto-forward updates, forwarding-address create/delete, send-as create/delete/verify, and changes to nonprimary send-as aliases. The same optional service account must receive the exact `gmail.settings.basic` and `gmail.settings.sharing` scopes from the Workspace administrator. These requests require an explicit Gmail grant and mint only those two scopes for the freshly verified owner; they never reuse the Keep scope. Ordinary mail operations and primary send-as updates retain user OAuth. The DWD-only sharing scope is omitted from regular OAuth consent. Canonical commands and equivalent Discovery API methods apply the same routing. See [Google's delegate guide](https://developers.google.com/workspace/gmail/api/guides/delegate_settings) and [send-as update requirements](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.settings.sendAs/update).

Maps uses the optional service-only `GOOGLE_MAPS_API_KEY` secret. Its metadata declares API-key authorization; selecting Maps adds no fictitious OAuth scope. The owner explicitly selects Maps and still verifies their Google identity. Calendar location searches require both Calendar and Maps grants. The key enters only the private in-process invocation for Maps commands or requested Calendar lookups and never appears in ordinary Calendar requests, model responses, or artifacts. Restrict the key to the required Google Maps Platform APIs and configure billing/quotas in the operator's Google project. Capabilities expose only the boolean `google_maps` flag.

## Adding a provider

Add a trusted `ServiceProvider` implementation to `src/providers.ts` and a matching application manifest under the repository's `src/connectors/`. A provider supplies fixed OAuth endpoints, scope selection, account/subject parsing, an operation validator, a mandatory confirmation policy, and a prepared execution request. Mark mutating operations as requiring confirmation in both manifests; those operations reuse the durable invocation ledger. HTTP providers declare allowed API origins and return `transport: "http"`; the reviewed gogcli port uses `transport: "native"` and runs inside the DO. They reuse the vault's authorization, encryption, refresh, disconnect, and bounded request handling. No end user can upload provider code or provide an arbitrary endpoint.

## Local checks

From the repository root:

```sh
npm run check:connectors
npx vitest run tests/connectors/service*.test.ts
npm run test:connectors
```

The native suite uses the same compatibility date as the repository and explicitly mocks all provider calls. The native port is vendored from the reviewed gogcli fork with a content-hash manifest. See the repository connector setup guide for deployment, secrets, consent-screen configuration and the required named service binding.
